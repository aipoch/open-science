## Rendering measurements

On the local macOS Electron software-rasterized capture host, the large-record Stage fixture rendered 3,223 DOM nodes and 694,974 displayed characters, paginated 3,000 material versions in 40-item pages, and reached a capture-ready frame after an end-of-record seek in 280.5 ms. These are fixture measurements, not a claim about cold-loading every possible `.science` archive. The test records node count, displayed-character count and seek latency as an attachment, and enforces explicit bounds.

Pixel reproducibility applies to the same build, browser, system-font configuration, viewport, resources and fixed software rasterizer. The isolated capture host disables hardware acceleration before Electron is ready; the normal interactive workspace retains GPU acceleration. GPU cold/warm path rasterization can differ at anti-aliased curved edges, so this guarantee does not cover live GPU-window pixels or different operating systems. Resource readiness lets interactive playback continue without waiting for each capture frame. Capture readiness additionally crosses a paint boundary after the current logical frame commits, cancels superseded seeks, and includes timeout placeholders. The sequential/direct-seek comparison and the font-timeout/late-font native-capture comparison each passed six repeated runs with strict PNG equality; all seven Stage desktop checks passed together. Complex or active formats may use a labeled static fallback. MP4 encoding, audio and video export jobs are outside this release.

The historical pilot publication archive was subsequently located and tested in an isolated desktop profile. The existing 50.2 MiB, schema-version-1 archive passed all 112 inventory checksum/size checks. The production adapter retained all 7 messages, 19 tool activities, 2 Notebook runs, 17 artifact versions and 1 uploaded input archive, with no unassigned records. It produced one branch with 28 steps and 112 seconds of reconstructed presentation time. Both Notebook runs joined their original tool invocations; the 17 publication calls share one step, whose bounded preview points to the complete original evidence.

That real-archive journey exposed and corrected two integration defects: Notebook details incorrectly required a live workspace path even though native import clears it, and material actions treated uploaded files as artifacts. Detail reads now use the existing persisted reference and exact run identity without initializing a runtime. Material previews retain archive membership, owner and immutable-version checks for both resource types.

After correction, the complete Electron journey passed in 44.9 seconds: native import, paused default, play/pause, end seek and rewind, all-materials access from the starting position, the real SVG and analysis-code previews, the uploaded ZIP fallback with enabled download and verified version bytes, full first-Notebook script and saved-output inspection, a question with fixed evidence, and restart into the same discussion and paused step. Both Notebook records and their invocation mapping were checked; detailed UI inspection covered the first run. The source records, Notebook history and original archive checksum remained unchanged. One deterministic test-provider request verified question delivery and persistence, not the quality of scientific answers. Private archive contents, scripts and screenshots remain outside the repository.

This archive records an offline reanalysis/publication of one historical experiment. It does not contain the entire original project or original research conversation, and it reports missing environment lock files. This validation did not execute archived analysis, start new experiments, restore another device or claim a frame-by-frame recording of the original game.

## Persistence and retention boundaries

Research drafts and send intents use local durable records with independent identities. Attachments become immutable versions before a successful save acknowledgement. Draft-only versions remain private until a real message publishes them through the existing upload lifecycle.

Explicitly discarding a saved draft may release a provably private, unreferenced version through the existing content cleanup owner. Cleanup is conservative when another window, a published Files entry, a message, another draft, a saved submission or another durable resource may reference it. Cancelling a queued question preserves a recoverable question and its attachments. Automatically clearing a composer never races to delete bytes belonging to a captured send.

The question journal retains accepted receipts for deduplication and cancelled questions for recovery. Very long discussion histories still have a linear journal scan/list cost; this is separate from the bounded archive-preview cache. Playback checkpoints and question-context mappings are local application data and are not added to `.science`.

The full unit run reported **44,032 passed, 12 failed and 780 skipped**. The failures were confined to `shell-process.test.ts` and `runtime-service.macos-isolation.integration.test.ts`: a cancellation lacked verified process termination, and an incomplete native sandbox cleanup left its owner active, causing subsequent tests to fail. The remaining directory/runtime-state difference is not diagnosed, so this is not a claim that the full local suite was green or that an upstream defect was established. No cleanup assertion or sandbox rule was relaxed.

## Reproduce the checks

Run the unit/architecture/database suite with `npm test`, the two TypeScript checks, `npm run db:schema:check`, `npm run check:web-api-map`, and the i18n guard. Build the desktop test application with `npm run build:e2e`, then run the `replay-stage`, `research-replay`, `research-replay-concurrency`, `research-replay-navigation`, `research-replay-notebook`, `session-package` and `session-fork` Playwright specs. These specs are registered in the existing CI test commands.

Validation results and any host-specific test limitations are reported in the PR. This document identifies the evidence and its limits; individual passing unit tests do not replace the desktop journeys.
