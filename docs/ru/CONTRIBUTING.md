# Как внести вклад в Open Science

Спасибо за интерес к участию в проекте! В этом документе описано, как подготовить
проект к работе, какой процесс разработки мы используем и какие проверки должно
пройти изменение перед слиянием.

## Кодекс поведения

Во всех обсуждениях сохраняйте уважительный и конструктивный тон. Исходите из
добрых намерений собеседников, сосредотачивайтесь на технической стороне вопроса
и помогайте создавать доброжелательную среду для всех участников проекта.

## Начало работы

### Требования

- [Node.js](https://nodejs.org/) 22 (см. [`.nvmrc`](../../.nvmrc)) и npm
- Git

### Настройка

```bash
# Fork the repo at https://github.com/aipoch/open-science/fork, then:
git clone https://github.com/<your-username>/open-science.git
cd open-science

# Add the original repo as upstream (to stay in sync)
git remote add upstream https://github.com/aipoch/open-science.git

npm install
```

Команда `npm install` выполняет шаг `postinstall`: генерирует клиент Prisma и
устанавливает нативные зависимости Electron-приложения.

### Запуск в режиме разработки

```bash
npm run dev
```

## Навигация для Агента-разработчика

Команды установки, разработки и проверки запускайте из корня репозитория:

| ---------------------- | ----------------------------------------------------------- |
| Установка              | `npm install`                                               |
| Запуск                 | `npm run dev`                                               |
| Целевой тест           | `npm test -- <affected-test-path> [-t '<test pattern>']`    |
| Тесты модуля           | `npm run test:module -- <module-id>`                        |
| Тесты затронутого кода | `npm run test:affected -- --base <base> --head <head>`      |
| Проверка типов Node    | `npm run typecheck:node`                                    |
| Проверка типов Web     | `npm run typecheck:web`                                     |
| Линтинг                | `npm run lint`                                              |
| Полный резервный набор | `npm run typecheck`, `npm run lint`, затем `npm test`       |
| UI E2E                 | `npm run build:e2e`, затем `npm run test:e2e`               |
| Сценарии UI            | `npm run build:e2e`, затем `npm run test:e2e:journey`       |
| Рабочее пространство   | `npm run build:e2e`, затем `npm run test:e2e:workspace`     |
| Доступность            | `npm run build:e2e`, затем `npm run test:e2e:accessibility` |
| Визуальные тесты       | `npm run build:e2e`, затем `npm run test:e2e:visual`        |

Создавайте рабочие деревья Git только в каталоге репозитория `.worktree/<name>`;
ветка каждого изменения должна основываться на ветке по умолчанию. Не удаляйте и
не перемещайте чужие рабочие деревья.

Получите явное разрешение перед разрушительными операциями с Git или файловой
системой, установкой зависимостей, при которой загружается или выполняется новый
код, публикацией пакетов или выпусков, работой с учётными данными вне
предусмотренных проектом процессов, а также перед не запрошенными в задаче
операциями записи во внешние системы, например отправкой изменений (push),
созданием Pull Request или issue и отправкой сообщений.

Перед изменением одной из следующих областей прочитайте соответствующий документ
владельца, а затем выполните профильные проверки:

| Notebook | [Текущая архитектура](../PRD.md#8-current-architecture-what-is-actually-implemented) | `npm run typecheck:node`; целевые тесты в `src/main/notebook/`                                 |

## Структура проекта

Это Electron-приложение, созданное с помощью electron-vite, React и TypeScript.
В каталоге `src/` находятся три слоя среды выполнения, соответствующие процессам
приложения, и общий модуль:

- `src/main/` — основной процесс Electron (среда выполнения ACP, сохранение
  сессий, артефакты, Notebook, проекты и обработчики IPC).
- `src/preload/` — preload-мост, предоставляющий renderer-процессу типизированный
  API `window.api`.
- `src/renderer/` — интерфейс на React (страницы, хранилища и компоненты).
- `src/shared/` — типы и вспомогательные функции, общие для процессов.

## Процесс разработки

1. Создайте для своего изменения ветку от ветки по умолчанию.
2. Внесите изменение, ограниченное поставленной задачей и самодостаточное.
3. Добавьте или обновите тесты, покрывающие изменённое поведение.
4. Сформируйте итоговый Test Impact Set и запустите его после последнего
   существенного изменения. Если нельзя достоверно определить владельца,
   потребителей или риски, используйте полный резервный набор проверок.
5. Откройте Pull Request с понятным описанием изменения и его мотивации.

### Долгоживущие внешние компоненты

Прежде чем добавлять ресурс, который существует дольше создавшего его процесса
вне управляемого приложением хранилища или в контуре управления стороннего
сервиса, следуйте [контракту владения долгоживущими внешними компонентами](../PRD.md#durable-external-component-ownership).
Тот же контракт действует при добавлении нового пути создания, принятия под
управление или удаления существующего компонента. В Pull Request необходимо
указать:

- модуль, владеющий компонентом, а также точные идентификационные данные или
  подтверждение, зафиксированные при создании;
- поведение при создании и запуске, остановке, удалении, восстановлении после
  сбоя и удалении приложения;
- как очистка завершается безопасным отказом, не сканируя системные каталоги и
  не затрагивая общие, пользовательские или иные ресурсы, право владения
  которыми не доказано;
- платформенные тесты порядка «остановить перед удалением», повторных попыток,
  идемпотентности и сохранности ресурсов, которыми приложение не владеет; и
- влияние на сохраняемые форматы, историческую совместимость или новое
  состояние.

Недостаточно пообещать добавить механизм очистки в будущем: не поставляйте
возможность создания компонента, пока его владелец не умеет безопасно остановить
и удалить этот компонент. Если Pull Request изменяет известное исключение для
устаревшего кода, перечисленное в контракте, он должен либо обеспечить для этого
пути подтверждённое владение, либо задокументировать ограниченное исключение и
план исторической совместимости. Не используйте исключение как прецедент для
нового поведения.

### Изменения схемы базы данных

Файл `prisma/schema.prisma` определяет таблицы, столбцы, значения по умолчанию,
индексы и внешние ключи. Ограничения SQLite CHECK, которые невозможно выразить
в Prisma, находятся в `prisma/sqlite-check-constraints.json`. Модуль схемы для
среды выполнения генерируется: не редактируйте его и не добавляйте в код запуска
DDL, относящийся к отдельным функциям продукта.

1. Измените схему Prisma и, только при необходимости, контракт SQLite CHECK.
2. Выполните `npm run db:schema:generate` и проверьте сгенерированную целевую
   схему.
3. Добавьте новую неизменяемую запись в `src/main/database/migrations/`; никогда
   не изменяйте выпущенную миграцию и не расширяйте зафиксированный список
   исправлений устаревшей миграции `0001`.
4. Перед коммитом выполните `npm run db:schema:check` и тесты миграций.

Prisma CLI используется только при разработке и в CI. Упакованные приложения
выполняют сохранённый в репозитории манифест миграций и не включают движок Prisma
migrate.

За историю миграций отвечает `src/main/database/`. Тесты модулей могут запускать
`migrateApplicationDatabase`, чтобы создать фикстуру с актуальной схемой. При
этом созданные вручную исторические схемы, проверки обновления и ожидаемое
содержимое журнала миграций должны проверяться в тестах миграций базы данных, а
не в наборах тестов функциональных модулей.

### Имена веток

Используйте формат `<type>/<short-description>` с описанием в нижнем регистре,
слова в котором разделены дефисами:

```text
feat/project-sidebar-filter
fix/notebook-kernel-timeout
ci/ai-pr-review
```

Используйте один из следующих стандартных префиксов типа:

- `feat` — новая функция
- `fix` — исправление ошибки
- `docs` — изменения только в документации
- `style` — форматирование и другие изменения, не влияющие на поведение
- `refactor` — изменения кода, которые не исправляют ошибку и не добавляют
  функцию
- `perf` — улучшения производительности
- `test` — добавление или исправление тестов
- `build` — изменения системы сборки или зависимостей
- `ci` — изменения конфигурации CI или скриптов
- `chore` — обслуживание, не относящееся к другим типам
- `revert` — отмена предыдущего изменения

### Стиль кода

- Соблюдайте стиль соседнего кода: правила именования, структуру и принятые
  идиомы.
- За форматирование отвечает Prettier. Команда `npm run format` необязательна;
  перед коммитом проверьте внесённые ею изменения, поскольку она перезаписывает
  файлы во всём репозитории.
- ESLint обеспечивает соблюдение правил линтинга; выполните `npm run lint`.
- Оборачивайте видимые пользователю строки функцией перевода `t()` из
  `react-i18next`. Добавляйте соответствующие переводы в пространство имён
  `renderer` в файлах `src/shared/i18n/locales/es.json` (испанский),
  `src/shared/i18n/locales/fr.json` (французский),
  `src/shared/i18n/locales/ja.json` (японский),
  `src/shared/i18n/locales/ko.json` (корейский),
  `src/shared/i18n/locales/pt-PT.json` (европейский португальский),
  `src/shared/i18n/locales/ru.json` (русский),
  `src/shared/i18n/locales/zh-Hans.json` (упрощённый китайский) и
  `src/shared/i18n/locales/zh-Hant.json` (традиционный китайский). В качестве
  ключа перевода используйте английский текст. Комментарии в коде и
  документацию пишите на английском языке.

## Политика проверки

### Неизменная семантика тестовых команд

- `npm test` всегда запускает полный переносимый набор Vitest. Смысл команды не
  зависит от текущей ветки или изменённых файлов.
- `npm test -- <paths> [-t '<pattern>']` запускает только цель, явно указанную
  при вызове. Команда не обнаруживает затронутые тесты, и её нельзя описывать
  как полную проверку.
- Отбор тестов с учётом влияния изменения — отдельное решение, основанное на
  итоговом diff. Не перегружайте `npm test` неявным поведением, зависящим от Git
  diff.

### Внутренний цикл

Во время реализации запускайте минимальный тест из имеющихся в проекте, который
проверяет изменяемое поведение. Повторяйте его после каждого изменения этого
поведения. Результаты внутреннего цикла для более раннего состояния реализации
не являются итоговым подтверждением.

### Итоговый локальный Test Impact Set

Перед передачей результата сформируйте минимальный набор на основе итогового
существенного diff:

1. тесты поведения, за которое отвечает изменённый модуль;
2. контрактные тесты изменённых интерфейсов и адаптеров;
3. тесты потребителей или функционального среза, если интерфейс мог измениться;
4. проверки типов для каждого затронутого процесса приложения;
5. `npm run lint`, если изменился исходный код или конфигурация, проверяемая
   линтером;
6. проверки платформы, сохранения состояния, миграций, сборки или E2E для
   рисков, которые можно воспроизвести локально.

Близость каталогов сама по себе не доказывает влияние. Если файл объединяет
несколько обязанностей, считайте изменение затрагивающим интерфейс или
используйте полный резервный набор проверок.

`test:module` поддерживает только идентификаторы модулей, объявленные в
`scripts/ci/module-impact.json`. Команда запускает подобранные для модуля тесты
владельца, контракта и репрезентативных потребителей; она не обеспечивает полную
проверку зависимых компонентов при изменении интерфейса. Если изменился
интерфейс или его потребители, используйте `test:affected` либо план PR Gate для
точной версии head.

### Полный резервный набор проверок

Выполните `npm run typecheck`, `npm run lint` и `npm test`, если выполняется хотя
бы одно из следующих условий:

- невозможно определить модуль-владелец, изменённый интерфейс или потребителей;
- меняются глобальные входные данные проверки, включая метаданные пакета,
  конфигурацию TypeScript/Vitest/сборки, workflow PR Gate или классификатор, а
  также правила маршрутизации по владельцам, потребителям, возможностям или
  резервным сценариям в манифесте влияния модулей;
- изменение пересекает несколько областей среды выполнения без доказанной карты
  влияния;
- workflow для кандидата на выпуск или сопровождающий явно требует полный
  локальный набор.

Полный резервный набор — это механизм безопасности, а не безусловное требование
для каждого Pull Request. От участников не требуется локально воспроизводить
каждую ветку CI для отдельной операционной системы.

Изменение только `testFiles` в модуле с уже определённым владельцем не требует
полного резервного набора. Вместо него запустите тесты проверки манифеста,
`npm run test:module -- <module-id>`, проверки типов затронутых процессов и
линтинг; CI, запущенный для точной версии head, остаётся главным источником
результатов полного переносимого и платформенного наборов.

### Решающая роль CI и подтверждающие данные

PR Gate классифицирует итоговый diff между base и head на основе доверенных
входных данных, добавляет ветки проверок для потребителей и платформенных рисков
и при неизвестном или неоднозначном владении безопасно выбирает полный план.
Выбранные проверки блокируют слияние; невыбранные отмечаются как пропущенные и не
считаются подтверждением.

При итоговой передаче результата перечислите существенные изменения, сопоставьте
каждое затронутое поведение с принадлежащей проекту проверкой и её итоговым
результатом (`behavior -> command -> result`), объясните, почему ветки проверок
для потребителей и платформ были включены либо исключены, и укажите непокрытые
риски. Отметьте, что проверки выполнялись после последнего существенного
изменения. Считайте изменение проверенным только после того, как независимая
проверка подтвердит, что это сопоставление охватывает итоговое состояние.

## Сообщения коммитов

Тема каждого коммита должна соответствовать Conventional Commits и включать
scope:

```text
<type>(<scope>): <description>
```

Этот формат проверяется для каждого коммита в Pull Request.

Используйте те же стандартные префиксы типа, что перечислены в разделе
[«Имена веток»](#имена-веток). Значение scope должно быть коротким именем затронутой
области в нижнем регистре, слова в котором разделены дефисами; внутри имён
собственных и технических терминов допустимы заглавные буквы (например,
`macOS`).

```text
feat(projects): add sidebar filter
fix(notebook): prevent kernel startup timeout
ci(review): unify automated AI reviews
```

- Напишите понятное описание в повелительном наклонении, которое начинается со
  строчной буквы; заглавные буквы допустимы внутри имён собственных и
  технических терминов (например, `detect user-installed CRAN R on Windows`).
- Сохраняйте тему краткой; если причина изменения не очевидна из diff, объясните
  её в теле сообщения.
- Для несовместимых изменений добавьте `!` перед двоеточием и завершающую строку
  `BREAKING CHANGE:`, например
  `feat(api)!: remove legacy session endpoint`.

## Pull Request

- Для заголовка Pull Request используйте тот же формат
  `<type>(<scope>): <description>`, например
  `feat(projects): add sidebar filter`.
- Укажите в описании все связанные issue.
- Для изменений, влияющих на поведение, используйте краткое описание, чтобы до чтения diff
  ревьюеры могли оценить замысел, объём и проверку. Там, где это уместно,
  используйте следующую структуру:

  ```md
  ## Problem

  ## Proposed change

  ## Scope and non-goals

  ## Acceptance criteria and validation

  ## Review focus
  ```

- Для архитектурных изменений, потоков данных, переходов состояний или
  взаимодействий нескольких компонентов рассмотрите возможность добавить
  диаграмму Mermaid, если с ней решение будет проще понять и проверить.
- Для небольших изменений в документации, работ по сопровождению и
  узконаправленных исправлений достаточно краткого резюме, однако в нём всё
  равно следует указать ожидаемое поведение и способ проверки.
- Включите итоговое сопоставление затронутого поведения с подтверждающими
  проверками из раздела
  [«Политика проверки»](#политика-проверки), укажите, что перечисленные проверки
  выполнялись после последнего существенного изменения, и назовите непокрытые
  риски.
- Ограничивайте Pull Request разумным объёмом и одной задачей, чтобы его было
  удобно проверять.
- Убедитесь, что итоговый Test Impact Set или, при необходимости, полный
  резервный набор проверок проходит успешно.
- После успешного прохождения проверок сливайте Pull Request напрямую и **только
  методом squash merge**. Не обновляйте ветку лишь потому, что `main`
  продвинулась: обновление требуется при конфликтах слияния или по просьбе
  сопровождающего. Тема squash-коммита должна сохранять формат Conventional
  Commit из заголовка Pull Request.
- При слиянии в `main` изменений, затрагивающих не только документацию,
  запускается [workflow Nightly](../../.github/workflows/nightly.yml), который
  проверяет полученный коммит после слияния и сертифицирует
  кроссплатформенные пакеты.

## Сообщения об ошибках

При создании отчёта об ошибке укажите:

- Ожидаемое и фактическое поведение.
- Шаги для воспроизведения.
- Операционную систему и версию приложения.
- Относящиеся к проблеме журналы или снимки экрана, если они доступны.

## Публикация пакета npm

Сопровождающим следует использовать [руководство по выпуску пакета npm](../npm-release.md).
Версии пакета npm используют теги `npm-v*` и публикуются через защищённый workflow
`Publish npm package`.
